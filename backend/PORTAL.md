# 마이페이지 / 관리자 조회 v0.1

사용자가 승인한 B안: 화면 + 조회 API. 등록/수정은 다음 PR로 분리합니다.
이 PR은 준비 코드이며 실제 홈페이지, Cloud Run, Neon, IAM을 변경하지 않습니다.
기준 브랜치는 `feat/backend-auth-foundation`입니다. 별도 PR #4 주문 테스트를 임의 병합하지 않습니다.

## 화면과 데이터

| 화면 | 구현한 조회 |
|---|---|
| `/portal/mypage` | 표시 이름 / 가입일 / 연결된 소셜 로그인 종류 / 본인과 연결된 주문 목록 |
| `/portal/admin` | 회원·강의·결제 대기 주문 집계 / 회원 목록 / 강의 목록 / 신청·주문 목록 |

관리자 화면의 검색 / 상태 필터 / 이전·다음 페이지 / 새로고침을 같은 출처 API에 연결했습니다.
회원명·강의명·기수는 부분 검색이며 `%`, `_`, `\`는 문자 그대로 검색합니다.
회원번호·주문번호·전화번호·이메일은 정확히 일치하는 값으로 검색합니다. 전화번호는 저장 형식(하이픈 없는 값)입니다.
목록은 최대 50개, UI 기본 20개이며 생성일·ID 내림차순입니다. offset 최대 10,000.
초기 소규모 목록용 offset 방식입니다. 동시 등록 사이의 페이지 이동에서는 중복/누락이 있을 수 있으며, 성장 시 커서 페이지 방식으로 개선합니다.

아직 결제는 `pending_payment`만 존재합니다. 주문을 수강 확정 / 결제 완료 / 매출로 표시하지 않습니다.
수강기간, 결제·다시보기는 명시적으로 준비 중입니다. 실제 소셜 연결/약관 동의/계정 연결/정보 수정/환불/알림은 없습니다.
회원 연락처 컬럼은 현재 존재하지 않으므로 없는 데이터를 만들어 보여주지 않습니다.
관리자 주문 목록의 전화·이메일은 DB SELECT에서 마스킹하며 원문은 응답하지 않습니다.
회원 목록과 비회원 포함 주문 목록은 구분합니다.

## 조회 API

모든 새 데이터 API는 GET입니다.
- `/portal/api/me`: 서버 세션에서 확인한 회원만 조회.
- `/portal/api/me/orders`: 서버 세션의 member_id로만 주문 소유 범위를 제한.
- `/portal/api/admin/summary`: require_admin으로 요약 조회.
- `/portal/api/admin/members`: require_admin / q / status / limit / offset.
- `/portal/api/admin/courses`: require_admin / q / enabled / limit / offset.
- `/portal/api/admin/orders`: require_admin / q / linked / limit / offset.

새 등록·변경·소유권 연결 API는 제공하지 않습니다. UI 로그아웃만 기존 auth API를 재사용합니다.
일반 회원이 관리자 화면의 HTML 틀을 열더라도 데이터 API는 403으로 차단합니다.
로그인이 없으면 401, 잘못된 조건은 입력 내용을 되돌리지 않는 422, DB 장애는 503입니다.
실패를 빈 목록/0건으로 바꾸지 않으며, 화면에 로그인 필요/권한 없음/로딩/빈 결과/오류·재시도를 구분합니다.
인증이 사라지면 목록 DOM을 지우고, 뒤로가기 복원 시 다시 인증 상태를 확인합니다.

## 주문 소유권의 경계

`003_portal_read_models.sql`은 **검토·테스트용 미적용 마이그레이션**입니다.
기존 orders를 수정하거나 고객 데이터에 소유자를 채우지 않고 `richon.member_order_links` 하나를 추가합니다.
order_id PK/FK + member_id FK로 1개 주문의 소유자가 1명만 존재하도록 합니다.
로그인 후 신규 주문 생성에서 검증된 세션으로 연결하거나, 과거 비회원 주문의 별도 소유 확인을 통과한 뒤에만 연결해야 합니다. 이 쓰기 흐름은 이번 범위 밖입니다.
이름/전화번호/이메일 일치만으로 자동 연결하지 않습니다. 기존 비회원 주문은 관리자에게는 보이지만, 일반 회원에게는 링크가 없으면 보이지 않습니다.
CI에서만 가상 회원 A/B에게 별도 테스트 주문을 명시 연결해 검증합니다.
`portal_migrate.py --apply`는 001/002 체크섬·이력을 확인하고 트랜잭션으로 적용하도록 준비했습니다. 앱 시작 시 DDL을 실행하지 않습니다.

## 배포 전 경계

기본 `RICHON_PORTAL_ENABLED=false`. 활성화에는 기존 `RICHON_AUTH_ENABLED=true` 및 올바른 auth origin 설정이 필요합니다.
UI와 API를 같은 출처로 제공하는 구성입니다. 별도 서버/호스팅/로그인 시스템을 추가하지 않습니다.
실제 서비스 도메인과 프록시/IAM 경계는 외부 로그인 연결 시 승인받습니다. 기존 비공개 Cloud Run 전체를 공개하지 않습니다.
portal의 HTML/CSS/JS만 명시적 파일 허용목록으로 제공하며 디렉터리 탐색은 없습니다.
인증 데이터와 응답은 `no-store`, HTML은 CSP/self-only 리소스, no-referrer, frame-ancestors none입니다.
새 조회 SQL 트랜잭션은 read_only=True입니다. 단 기존 세션 검증의 last_seen/idle 만료 갱신은 기존 auth 동작대로 수행합니다.

공개 전에 002/003 실제 적용, 최소권한 DB 계정, 관리자 지정 승인, OAuth 연결/가입 동의, 도메인·브라우저 쿠키 검증이 필요합니다.
관리자 GET 검색 조건에는 개인정보가 들어갈 수 있으므로 공개 시 게이트웨이/Cloud Run 요청 URL·쿼리 로그와 보관 정책을 확인하고 검색어가 그대로 기록되지 않도록 처리해야 합니다. 이 PR은 해당 인프라 로깅을 변경하지 않습니다.
응답·쿼리 본문·원문 예외는 앱 코드에서 로그로 남기지 않습니다. 아직 관리자 조회 감사 기록/요청 제한은 후속 공개 준비 범위입니다.

## 검증

- 기존 백엔드 CI에서 단위/API 계약 검사와 실제 임시 PostgreSQL 세션·권한·조회·소유권 격리 검사.
- 동일 이름·연락처의 다른 회원/미연결 주문이 섞이지 않는지 확인.
- 관리자 권한 삭제/회원 정지/로그아웃 시 다음 요청 차단.
- 마스킹/SQL 인젝션·와일드카드/페이지 제한/누락 스키마/읽기 전용 트랜잭션 검사.
- `portal_browser.py`: 격리된 로컬 UI + 가상 API 응답으로 Chromium 데스크톱/모바일, 탭·검색·페이지, 오류·재시도, 권한 안내, 문자열 XSS, 로그아웃 DOM 정리 검사.
- 브라우저의 가상 API 테스트와 실제 DB API 테스트를 분리합니다. 실제 카카오/네이버·Cloud Run·Neon 종단간 시험을 의미하지 않습니다.
- Docker는 신규 준비 DDL/테스트/문서를 제외하고 실제 런타임 모듈+화면만 포함. 기본 OFF 404 검사.
