# 선택 상담정보 동의 철회 / 출시 전 구현

2026-09-24 / PR24 후속. PR24는 09:02:16 UTC에 실제 병합되었다(9c63f75fb0237c8d43cccf1b370e1af696b06186). 가입정보 구현은 다시 작성하지 않는다. 이 후속은 기존 feat/signup-consent-policy에서 작업하며, 코드 저장/검사와 운영 반영을 구분한다.

## 이번 변경

마이페이지의 선택 상담정보 동의 철회 기능을 기본 OFF로 준비한다. 활성화된 서버가 본인 /me 응답에 consultation_withdrawal_available=true를 명시하고 현재 선택동의가 true인 경우에만 버튼을 표시한다. 취소 가능한 확인 후 POST /portal/api/me/consultation-consent/withdraw로 {"confirm":true}만 보낸다.

서버는 기존 인증 세션, 정확한 Origin, 세션에 묶인 CSRF를 검사한다. 대상 회원번호/연락처/권한을 클라이언트 입력으로 받지 않는다. 같은 트랜잭션에서 회원과 세션을 잠그고 현재 회원상태/권한/인증버전/만료/철회 여부를 재확인한다. 다른 회원이나 주문/수강권/로그인 연결을 변경하지 않는다.

member_profiles의 age_range/gender를 NULL, consultation_consent를 false로 바꾸고 consultation_withdrawn_at에 처음 처리한 시각만 남긴다. 등록 당시 consented_at, 이름/전화/이메일, 회원번호는 유지한다. 반복 요청은 첫 철회시각을 보존하며 처음부터 미동의인 회원에게 시각을 만들어 넣지 않는다. 이전 가입 티켓으로 선택정보를 다시 덮어쓰지 않는다. 커밋 실패는 성공으로 응답하지 않는다.

화면은 서버의 명시적인 성공 응답 이후에만 선택정보를 비운다. 401은 개인정보를 지우고 로그인 안내, 403은 요청 검증 실패 안내, 503/네트워크 오류는 결과 미확인 안내다. 로그아웃/페이지 이탈 뒤 늦게 도착한 결과가 개인정보나 성공 문구를 되살리지 않으며, 늦은 CSRF 응답으로 새 요청을 시작하지 않는다.

## 변경하지 않은 것

실운영 DB009/010 적용, SQL 권한 부여, 서버 환경변수/태그/이미지, Worker/Access, Naver/Kakao 콘솔, 메인 메뉴, root 공개 약관/방침은 변경하지 않는다. 실제 고객 데이터와 제공자 토큰을 조회하거나 삭제하지 않는다. 기존 로그인 실계정 성공을 다시 초기화하지 않는다. 회원탈퇴/제공자 연결해제/백업 파기를 이 기능으로 완료 처리하지 않는다.

## 별도 승인 후 적용할 조건

1. 공개 개인정보처리방침에 선택 동의 철회 방법/선택정보 보유기간과 철회시각 기록의 목적/보유기간을 확정한다. 철회 기록을 영구 보존한다고 정하지 않는다. 공식 이메일/수탁자/국외처리/로그/백업/시행일은 아직 미확정이다.
2. 기존 DB009의 정확한 준비 상태를 확인한다. 010_consultation_withdrawal.sql은 nullable timestamp와 CHECK를 추가하며 기존 동의/회원행을 다시 쓰지 않는다. 전용 명시적 migrator는 의존 체크섬/ledger/advisory lock/단일 트랜잭션을 검증한다. 실행 권한이나 런타임 DDL을 추가하지 않았다.
3. 별도 소유자 검토로 프로필의 정확한 4개 열(age_range, gender, consultation_consent, consultation_withdrawn_at)에만 UPDATE 권한이 필요하다. 이름/전화/이메일/등록일 변경, 프로필 DELETE, schema_migrations 접근은 허용하지 않는다. 새 권한 적용 도구나 운영 GRANT를 이번에 실행하지 않았다.
4. RICHON_CONSULTATION_WITHDRAWAL_ENABLED=true는 양쪽 정책 member-info-v1과 AUTH/PORTAL 활성 상태에서만 허용한다. startup은 새 열/제약조건과 정확한 최소권한을 읽기 검증한다. 새 권한을 적용한 상태에서 member-info-v1 앱의 플래그만 false로 바꾸면 엄격한 권한 검사가 중단될 수 있으므로, 후보 전환/롤백 시 코드와 grants를 함께 검토한다. 검사를 완화해 통과시키지 않는다.
5. 기존 portal-candidate 태그는 현재 Worker가 사용 중이다. 별도 후보 계획 없이 이동시키지 않는다. 기존 Access를 유지한 상태에서 실제 본인 계정의 최초 철회/반복/로그아웃을 확인한 뒤 릴리스한다. 메뉴 일반 공개는 별도 승인이다.

## 파기의 범위 / 후속 회원탈퇴 설계안

온라인 DB 필드를 NULL로 바꾼 것은 과거 백업/WAL/복구 시점/수탁자 로그까지 물리 파기했다는 증거가 아니다. 복원 시 철회된 선택정보가 다시 나타나지 않도록 처리 절차와 실제 보유기간을 확정해야 한다. 별도 상담 기록이나 내보내기 파일로 이미 복제한 선택정보가 있다면 그 처리 경로도 확인해야 한다. 현재 이런 운영을 구현했다고 주장하지 않는다.

회원탈퇴는 별도 작업이다. 제안하는 다음 설계 단위는 같은 제공자/app/subject의 최근 재인증과 일회성 탈퇴 확인, 전체 세션 무효화, 보존 근거가 확인된 거래기록 분리, 프로필/연결정보 처리, 제공자 연결해제 및 실패 재처리다. 탈퇴 요청 수락/계정 이용 중단/연결해제 완료/온라인 정보 처리/백업 처리 완료를 구분한다. 제공자 오류 때문에 개인정보 처리를 무기한 계속하는 설계를 채택하지 않는다. 이 설계안을 실제 데이터 일괄삭제 승인으로 사용하지 않는다.

현재 로그인은 제공자 토큰을 영구 저장하지 않는다. 따라서 옛 세션만으로 제공자 연결해제가 가능하다고 가정하지 않는다. 새 재인증과 서버 내 단기 토큰 처리 또는 별도 허용된 API 경로를 설계해야 한다. 선택 상담정보 동의 철회에는 카카오/네이버 연결해제를 호출하지 않는다.
